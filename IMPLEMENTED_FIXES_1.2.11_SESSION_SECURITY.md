# 1.2.11 — безпека кімнатних сеансів і recovery

## Реалізовано

- `GET /api/rooms/:code/state` більше не автентифікує гравця через query-параметр `token`.
- Кімнатний токен передається лише в заголовку `X-Player-Token`; ідентифікатор — у `X-Player-Id`.
- `GET /api/rooms/recovery-status` більше не приймає `requestToken` у URL.
- Секрет recovery-запиту передається через `X-Recovery-Request-Token`.
- У кімнаті зберігається лише SHA-256-хеш секрету recovery-запиту.
- Схвалення хостом не повертає новий кімнатний токен через status-endpoint.
- Для отримання схваленого сеансу додано `POST /api/rooms/recovery-claim`.
- Claim є одноразовим: повторне отримання повертає HTTP 410.
- Після claim поле `grantedToken` очищується, а запит переходить у стан `consumed`.
- Старі записи з `requestToken` перетворюються на `requestTokenHash` під час нормалізації кімнати.
- Клієнт використовує двокроковий сценарій: опитування status, потім одноразовий claim.

## Регресійна перевірка

Оновлено `test_host_recovery_122.js`:

- перевіряється, що status не містить кімнатного токена;
- перевіряється одноразовий claim;
- повторний claim має HTTP 410;
- query-параметри `token` і `requestToken` відхиляються;
- у покімнатному JSON немає сирого `requestToken`;
- після claim `grantedToken` дорівнює `null`.
