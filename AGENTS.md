## Обов’язкові правила роботи з репозиторієм

Ці правила обов’язкові для всіх подальших змін у репозиторії.

### Гілки та Pull Request

1. Не змінювати `main` напряму.
2. Один логічний пакет змін має виконуватися в окремій гілці та оформлюватися окремим Pull Request.
3. Не поєднувати в одному PR незалежні виправлення, інфраструктурні зміни, UI-роботи та редизайн.
4. Не зливати Pull Request без прямої команди власника репозиторію: «злив».

### Межі реалізації

1. Не переходити до UI чи кінематографічного редизайну без окремої команди.
2. В інфраструктурних PR не змінювати стабільну ігрову логіку.
3. Не додавати до поточного пакета роботи, які не входять до погодженого технічного плану.
4. Якщо для виконання завдання потрібно вийти за погоджені межі, спочатку зупинитися й отримати окреме погодження.

### Перевірка перед реалізацією

1. Перед будь-якою реалізацією обов’язково повністю прочитати `docs/STABILIZATION_PLAN_1.2.11.md`.
2. Перед початком кожного пакета перевіряти актуальний стан:
   - коду;
   - тестів;
   - CI;
   - конфігурації середовища;
   - пов’язаних відкритих і завершених PR.
3. Актуальні код, тести та CI мають пріоритет над твердженнями застарілого технічного плану.
4. Не покладатися лише на пам’ять, попередні звіти або результати давніших перевірок.
5. Якщо фактичний стан відрізняється від технічного плану, спочатку документально зафіксувати розбіжність і її відомі або ймовірні причини, а вже потім переходити до реалізації.
6. Розбіжність між планом і фактичним станом не можна мовчки виправляти ані в коді, ані в документації.

### Тести та звітність

1. Не заявляти про успішне проходження тестів без фактичного результату виконання.
2. У звіті зазначати:
   - точну команду перевірки;
   - кількість пройдених, провалених і пропущених тестів;
   - відомі обмеження середовища;
   - перевірки, які не вдалося виконати.
3. Не приховувати помилки, попередження, пропущені тести або розбіжності між локальними результатами та CI.

### Технічний план

1. Після кожного завершеного етапу оновлювати канонічний технічний план.
2. У плані фіксувати:
   - що завершено;
   - що перевірено;
   - фактичні результати тестів і CI;
   - виявлені розбіжності;
   - наступний погоджений пакет;
   - роботи, які свідомо не входять до поточного етапу.
3. Оновлення плану має входити до того самого PR, якого стосується відповідний етап.
